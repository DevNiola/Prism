We welcome contributions to all parts of the Prism ecosystem!

## Areas for Contribution

### 1. Error Taxonomy

The most impactful way to help. Adding plain-English explanations for cryptic errors helps every developer.

### 2. Core Engine (Rust)

Improving state reconstruction speed, adding new trace annotations, or optimizing the replay sandbox.

### 3. Web & IDE Interfaces

Enhancing the visual trace viewer or adding new VS Code Quick Fixes.

## Development setup

Run the commands from the repository root unless indicated. Install Rust through rustup, Node.js 24, pnpm 9.15.9, and Docker with the Compose plugin. See the [Quickstart](/quickstart) and [source installation guide](/installation) for the CLI and source-build prerequisites.

### Build the workspace

```sh
rustup toolchain install stable --component rustfmt --component clippy --target wasm32-unknown-unknown
npm install --global pnpm@9.15.9
pnpm install --no-frozen-lockfile
cargo build --workspace --all-features
cargo run --bin grat -- --help
cargo install wasm-pack --locked
wasm-pack build crates/wasm --target web --release
pnpm run build:server
pnpm run build:web
pnpm run build:vscode
```

The Rust toolchain settings come from `rust-toolchain.toml`. The WASM package is written to `crates/wasm/pkg`. The `build:web` script generates the web taxonomy before building Next.js. Use `--no-frozen-lockfile` to install against the current manifests when they differ from the checked-in lockfile.

### Run the local stack

Build and start Redis, the API server, and the frontend with Compose.

```sh
docker compose up --build
```

The frontend is at `http://localhost:3000`, the API health endpoint is at `http://localhost:3001/health`, and Redis is on port `6379`. Run `docker compose down` to stop the stack while keeping the Redis volume.

For hot reload and API requests that invoke the local `grat` binary, start just Redis in Compose. Run the server and frontend in separate terminals from the repository root. Stop the full Compose stack first if it is running.

```sh
docker compose up -d redis
REDIS_URL=redis://127.0.0.1:6379 GRAT_BINARY="$PWD/target/debug/grat" pnpm run dev:server
```

```sh
pnpm run build:taxonomy
NEXT_PUBLIC_API_URL=http://localhost:3001 pnpm run dev:web
```

### Testing

The Cargo workspace command runs the Rust unit, integration, and documentation suites. Run the remaining commands for TypeScript, browser WASM coverage, taxonomy validation, and benchmarks.

| Check | Command |
| --- | --- |
| Full Rust suite | `cargo test --workspace --all-features` |
| Rust unit tests for library and binary targets | `cargo test --workspace --all-features --lib --bins` |
| Rust integration tests | `cargo test --workspace --all-features --tests` |
| Core library doctests | `cargo test -p grat-core --doc` |
| Server unit and API integration tests | `pnpm --filter grat-server exec vitest run` |
| Web unit tests | `pnpm --filter grat-web exec vitest run` |
| Browser end-to-end tests | `pnpm --filter grat-web exec playwright install chromium`, then `pnpm --filter grat-web exec playwright test` |
| WASM browser tests (requires Chrome or Chromium) | `wasm-pack test --headless --chrome crates/wasm` |
| Taxonomy lint | `bash scripts/lint_taxonomy.sh` |
| Core benchmarks | `cargo bench -p grat-core` |

The web test configs require development dependencies that are missing from the
current `grat-web` manifest. Install them in your local checkout before running
the web unit and end-to-end commands.

```sh
pnpm --filter grat-web add -D vitest @vitejs/plugin-react jsdom @playwright/test
```

This updates the local web manifest and lockfile. On Linux, use
`playwright install --with-deps chromium` if Chromium system libraries are needed.

## Pull Request Process

1. Fork the repository and create your feature branch.
2. Run the relevant checks under Testing.
3. Update documentation if you add new features or CLI flags.
4. Submit your PR and wait for a maintainer review.

## Commit messages and changelog

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)
for commit subjects that land on `main`. Use `type(scope): summary` with an
optional scope. For a squash merge, follow the same convention in the final
squash commit subject and preserve any breaking-change footer in its body.

| Commit example | Release impact |
| --- | --- |
| `fix(replay): handle an empty footprint` | Patch |
| `feat(cli): export replay profiles` | Minor |
| `docs(cli): explain RPC overrides` | No release on its own |

For a breaking change, include a `BREAKING CHANGE: <description>` footer
after a blank line in the commit body. Describe the behavior that changed and
how users can migrate. The current release analyzer uses semantic-release's
default Angular preset, so use the footer even if the subject contains `!`.

The [Release workflow](https://github.com/DevNiola/Prism/blob/main/.github/workflows/release.yml) runs on pushes to
`main`. [Semantic-release](https://github.com/DevNiola/Prism/blob/main/.releaserc.json) analyzes commits since the
last release tag and generates release notes when a commit warrants a release.
It prepends the generated notes to `CHANGELOG.md`, publishes the GitHub
release, and commits the changelog back to `main` in a
`chore(release): <version> [skip ci]` commit. Treat the file as generated.
Manual corrections to generated notes can be overwritten during regeneration.

### Backfilling hotfix entries

1. Check the hotfix tag, its GitHub release notes, and the commits included
   in the release. Record the shipped version and link to the original fix.
2. If the fix is absent from `main`, bring it in through a PR with a
   `fix(scope): summary` commit. Mention the hotfix version and original PR
   in the body so the next eligible release can trace the change.
3. If the fix is already tagged and only the notes are missing, a maintainer
   can amend that release's GitHub notes in place. Future semantic-release
   runs analyze commits after the latest release tag and prepend a new
   changelog section. For a correction to the historical
   `CHANGELOG.md` section, use a dedicated, maintainer-reviewed backfill
   PR with the shipped version and original fix link. Keep the existing
   release tag and avoid an empty `fix:` commit that would publish another
   patch.
